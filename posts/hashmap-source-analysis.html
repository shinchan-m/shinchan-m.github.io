HashMap 源码深度解析：从 put 到 resize

📅 2026-07-01  |  Java 源码分析 面试

面试必考题！逐行分析 HashMap 的 put 方法、哈希冲突解决、红黑树转换和扩容机制——不只是背八股，而是真正看懂源码。

面试为什么爱问 HashMap 源码而不是背八股

因为它一道题能考出四层东西：数组 + 链表 + 红黑树的组合设计、哈希扰动函数的用意、扩容时避免重算 hash 的技巧，以及 JDK 1.7 到 1.8 的改动动机。把这四层讲通，等于当场证明你真的打开过 java.util.HashMap 这个文件，而不是背了一份面经。

底层结构是一个数组 + 链表 + 红黑树

JDK 1.8 里，HashMap 的主体是 Node<K,V>[] table 这个数组，也叫桶（bucket）。发生哈希冲突时，同一个桶里的节点挂成链表；当链表长度 ≥ 8 且数组容量 ≥ 64 时，链表转成红黑树，把最坏情况的查询从 O(n) 降到 O(log n)。

注意这两个条件是「且」的关系：如果容量还不到 64，treeifyBin 会选择先扩容而不是树化——因为此时冲突多的真正原因是桶太少，扩容比换数据结构更划算。

put 方法流程

  1. 计算 key 的 hash：(h = key.hashCode()) ^ (h >>> 16)，把高 16 位异或进低 16 位，让高位也参与寻址，减少碰撞。
  2. 定位桶下标：(n - 1) & hash，在容量是 2 的幂时等价于取模，但位运算快得多。
  3. 桶为空，直接放入新节点，结束。
  4. 桶不空，先比较首节点的 key 是否相同，相同则准备覆盖 value。
  5. 首节点不同就遍历链表（或树），找到相同 key 则替换 value，否则尾插一个新节点。
  6. 插入后如果链表长度 ≥ 8，调用 treeifyBin 尝试树化。
  7. 最后自增 size，若超过 threshold 则触发扩容。
// JDK 1.8 HashMap#hash —— 扰动函数
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

// 为什么容量必须是 2 的幂：让 (n - 1) & hash 等价于 hash % n
// n = 16 时，n - 1 = 0b1111，正好掩掉高位，只留低 4 位做下标
index = (n - 1) & hash;

resize 扩容机制

每次扩容为原来的两倍。JDK 1.8 的巧妙之处在于不需要重新计算 hash：容量翻倍意味着下标多用到 hash 的一个新二进制位，所以只要看原 hash 值在这个新增位上是 0 还是 1，就能确定节点的去向。

  • 新增位为 0：下标不变，节点留在原位置（源码里的 lo 链）。
  • 新增位为 1：新下标 = 原下标 + 原容量（源码里的 hi 链）。

一次位运算替代一次完整的 rehash，这就是 1.8 相对 1.7 在扩容上的主要优化。

几个易错点

  • 容量为什么必须是 2 的幂？为了让 (n - 1) & hash 能等价于取模，同时保证位分布均匀。
  • 负载因子为什么默认 0.75？空间与时间的折中：再高冲突概率显著上升，再低则浪费内存、频繁扩容。
  • JDK 1.7 的头插法在 1.8 改成了尾插法，因为 1.7 在并发扩容时可能形成环形链表，导致 get 死循环。
  • 为什么用红黑树而不是 AVL 树？红黑树的插入旋转次数更少，在频繁写入的场景综合代价更低。
顺带一提：HashMap 本身不是线程安全的。上面第 3 条讲的死循环只是 1.7 的表现，1.8 改成尾插后不会再成环，但并发下依然会丢数据——要并发就用 ConcurrentHashMap。

能把「结构 → put → resize」这三层串起来讲清楚，HashMap 这道题就稳了。
